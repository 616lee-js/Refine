## Phase 6 — Background Summarization (Cabinet 2) — SUPERSEDED IN PART, see above

**Requirement:** The Cabinet 2 narrative summary must capture tonal and emotional context, not just topics.

The summary exists so that future sessions can open with appropriate awareness of where the user was last time — not just what they talked about, but how they were doing. A topic-only summary ("user discussed work stress, relationship difficulty") misses the thing that matters: was the user holding it together or barely keeping it together? Were things shifting? What was the emotional register of the session?

When designing the summarization prompt in Phase 6, the summary should answer:
- What was the user carrying? (topics + emotional weight)
- What was the tone and texture of how they were? (not just what was discussed)
- Was there any movement or shift during the session?
- Anything the next session should be gently aware of?

This is what enables the model to open a new session with calibrated presence rather than a blank-slate greeting that ignores history.

## Phase 6 — background processing must be serverless-compatible

**Requirement:** summary generation and memory extraction cannot be naive fire-and-forget.

The app now runs on Vercel. A serverless function is killed once it returns a response, so
work kicked off with an un-awaited promise after the response is sent will be terminated
partway through — sometimes, unpredictably, which is worse than failing outright.

**This was not hypothetical.** `/api/chat` and `/api/reflections/[id]/end` both shipped with
exactly this bug: the assistant entry save, the closing message save, and the `endedAt`
update all ran as un-awaited promises after `controller.close()`. Fixed 2026-07-29 —
reflections could otherwise have intermittently failed to save once deployed.

**Use `persistAfterResponse()` from `src/lib/after-response.ts`** for any write that has to
outlive a response. It wraps Next's `after()` (which maps to the platform `waitUntil`),
guarantees the held-open promise always settles so a function can never hang for its full
`maxDuration`, and logs failures. Two constraints it encodes:

- It must be called from the **route handler body**, not from inside a stream callback —
  `after()` requires an active request context.
- Streaming routes need `export const maxDuration = 60` (Hobby ceiling); the default is 10s,
  which an LLM completion plus a post-response write can exceed.

For work heavier than a couple of inserts — which Phase 6 summarization will be — prefer a
cron-driven worker over extending a user-facing request. A daily cron is already configured.

~~The `extraction_status` column already exists on `reflections` for exactly this lifecycle
(null → pending → running → succeeded/failed).~~ **Corrected 2026-10-12.** That column was
dropped on 2026-09-24, NULL on every row, and is not coming back — there is no `reflections`
table either. **Do not add a status column.** The summariser queue settled the same question
better: derive the work by joining entries against what they produced, so a run that dies
halfway leaves work due rather than rows stuck in "running" that something has to clean up.
`src/lib/summaries/queue.ts` is the pattern to copy, and Mirror's `usersDue()` is the
cross-entry version of it. See the note where the column used to be, in
`src/lib/db/schema.ts`.

## PROPOSAL — Archive ↔ Mirror (not built, awaiting approval)

Proposed 2026-09-21. No schema, no one-way door. Recorded because the two
surfaces now overlap and the overlap should be deliberate.

**The distinction to hold:** the Archive holds *records* — what happened, in the
order it happened. Mirror holds *what was derived from them* — threads, facts,
trends. Same underlying data, opposite direction of travel. The failure to avoid
is Mirror becoming a second list of entries, or the Archive growing a synthesis
panel; then there are two half-surfaces instead of two.

The archive's new topic chips make the join concrete, because a topic is now a
URL (`/reflections?topic=…`):

1. **Mirror → Archive.** A thread in Mirror links to the entries it was drawn
   from. Today a thread is a sentence with nothing behind it; "show me where this
   came from" is the obvious missing move, and it is now one link. Likewise a
   Trends card links to `?filter=checkin`.
2. **Archive → Mirror.** A topic chip that matches an existing thread links into
   it. One that does not offers "make this a thread", proposing a `user_memory`
   row of kind `thread` through the existing API — no new storage.
3. **What this does NOT become.** Mirror does not list entries, and the archive
   does not show threads inline. Each links to the other.

**Dependency:** both directions are weak until the topic-vocabulary consistency
review lands (see the content-pass queue). Matching "Dad" against a thread about
"my father" fails silently today, and a link that usually finds nothing is worse
than no link.

**Longer term:** the topic filter is the retrieval surface that Cabinet 3
embeddings eventually replace. Building it now costs nothing when that arrives —
the URL shape stays, the matching behind it gets better.

## Per-user summarisation personalisation — CONSIDERED AND DROPPED 2026-09-24

Proposed 2026-09-21: a user's corrections to their summaries would be stored as
per-writer "guidelines", injected into that user's summariser call, and mined for
few-shot examples. Two tables (`summary_guidelines`, `summary_evals`) plus a
`guideline_ids` column on `journal_entry_summaries`.

**Dropped before anything was built.** Nothing reached `src/` or `drizzle/`.
Deployment is a closed, controlled beta, and what the beta needs is evidence
about *the summariser*, not a hundred divergent per-writer configurations that
make it impossible to tell whether a prompt change helped.

Replaced by the summarisation evaluation log — built 2026-09-24. Same act by the
user, opposite destination: the assessment goes to a system-level log the product
owner reads, and **never alters that user's own future summaries**. See
`summary_evaluations` in `src/lib/db/schema.ts` and `/admin/summary-evals`.

Not to be re-proposed without a deliberate decision. If it ever returns, two
pieces of the original reasoning carried over and are worth keeping:

- **The rubric is plaintext, everything else encrypted.** The structured answers
  describe what the model did — they say nothing about the person, and
  aggregation is the whole point. "How often was a quote altered under v2 versus
  v3" has to be a SQL query, not a decrypt-every-row loop. The moment a note or a
  correction is involved it is the person's words, and those are encrypted like
  everything in Cabinet 1 and 2.
- **Snapshot, never link.** Summaries regenerate and entries get edited, so a row
  pointing at the live summary silently comes to describe something nobody
  judged. The assessment has to hold what was actually on screen.

One thing the original had that the built version deliberately does not: a
`guideline_ids` column recording which rules were in force. Unnecessary here —
the user can always edit their summary directly, so there is no rule state to
reconstruct.

### Summariser v2 — APPLIED 2026-09-24

Categories were coming back as one-off phrases ("the promotion", "Tuesday's
argument") because v1 told the model to use *the writer's own words*. A tag that
fits one entry groups nothing, so the archive's category filter never narrowed
anything.

Shipped:

- **A fixed vocabulary of nine life domains** — work, relationships, health,
  money, purpose, rest, community, personal growth, faith — defined once in
  `src/lib/summaries/categories.ts` and **interpolated into the prompt at call
  time**, so the markdown cannot drift from the code.
- **Enforced, not merely requested.** `refineCategories()` in
  `src/lib/summaries/parse.ts` resolves the model's output against the list
  (case-insensitive, deduped) and discards anything else before storage. The
  closed list is a guarantee rather than an instruction.
- **No hard cap per entry.** The prompt asks for restraint — most entries want
  one or two — but a long entry that genuinely ranges across six may carry six.
  `MAX_TOPICS` is now 9, the size of the vocabulary itself.
- **`[]` is a correct answer** when none of the nine fits. Forcing a domain onto
  an entry that has none is worse than leaving it uncategorised.
- **The writer is not constrained.** The correction UI offers the nine as
  toggles *plus* a free-text field. The machine is held to the list so its
  output groups; a person editing their own entry is not.
- **Changing the list re-summarises everything.** `SUMMARISER_VERSION` folds in
  a fingerprint of the vocabulary (`v2@2026-09-24+c9-wrhmprcpf`), so editing
  `categories.ts` is self-announcing. Without that, the model would be told
  something new while the version stayed identical, and the archive would hold
  two incompatible vintages with no way to tell them apart.

**Consequences to expect:**

- Every summary became due on deploy and re-summarises at 25/day.
- **Corrected summaries keep their old categories permanently.** The queue never
  writes `encrypted_user_content`, by design — so any summary edited by hand
  keeps whatever it was given, and those terms still appear in the category
  filter alongside the nine. Honest, since it is the writer's own text.

**Still owed:** the quotes-guidance rewrite. It was going to ride in this same
version bump and did not, so doing it later costs a second full re-summarise.

## PROPOSAL — Memory as measurements (not built, awaiting approval)

Proposed 2026-10-12, at the product owner's request. **Nothing here is built.**
Their words: *"Memory is an opportunity to capture patterns in topics, word
choice, entry length, and other data to correlate with insights or user
behaviors/well being… This will need more thought and planning what data could be
useful to track, but I would go wide first."*

This document is the wide version, for them to cut down.

### What it replaces, and what it does not revive

Memory generates nothing today. Everything in `user_memory` was typed by the
person. That is not an oversight — it was built and removed:

- `0009_legal_purifiers.sql` added `mirror_reviews.encrypted_findings` and
  `user_memory.mirror_review_id`.
- `0010_mean_firedrake.sql` removed both, the same day.

The note left behind: *"If anything ever proposes memory again, that is a
decision, not a column to restore."* The direction dropped was findings proposed
one at a time for approval, because **Mirror became a report to read rather than
lines to sort**.

**This proposal does not revive that.** It is a different thing in the same
place: Memory holding derived *measurements* about someone's writing, rather than
statements about their life. Worth being explicit, because the schema, the UI and
three documents still describe the dropped version as the plan.

### The shift, stated plainly

Today a Memory item is a sentence someone wrote about themselves, of a `kind`
(`fact`, `thread`, `preference`, `diagnostic_context`, `other`), stored encrypted.

What is proposed is a count, a length, a frequency, a distribution. Those are not
sentences, and that is the whole difficulty: every part of the current Memory —
the table shape, the Keep/Remove controls, the "waiting on you" callout, the
per-kind columns — was built for statements awaiting approval. None of it fits a
number.

### The catalogue — what could be tracked

Grouped by what it costs, because that decides what can ship first and what needs
a model call.

**Group 1 — no decryption at all.** Plain columns. Free, and available for every
account today.

| Signal | From |
|---|---|
| Entries per week, per month | `journal_entries.completed_at` |
| Gaps between entries, longest gap | same |
| Time of day someone writes | same |
| Day of week | same |
| How long an entry was open before being finished | `created_at` to `completed_at` |
| Whether an entry was returned to and edited | `updated_at` vs `completed_at` |
| Typed versus partly spoken | `modality` (`text` / `mixed`) |
| Check-in completion rate | `questionnaire_responses.completed_at` |
| Which frameworks get answered, and how often | `questionnaire_slug` |
| Distribution of safety tiers over time | `safety_log.tier`, `created_at` |
| How often someone re-reads their own record | `content_access_log` |

**Group 2 — needs decryption, no model call.** Everything here is already
decrypted by an existing pass, so this adds reading, not spend.

| Signal | From |
|---|---|
| Entry length, and how it changes | entry body |
| Which of the nine categories recur, and in what proportion | summary `topics` |
| Which people recur, and how often | summary `people` |
| How many entries are flagged `thin` | summary `thin` |
| Framework scores over time, and movement | `encrypted_scoring.total` |
| Sleep, mood, energy series | check-in answers |
| Which habits hold and which drift | check-in `kept_up` |
| Whether a summary was corrected by hand, and how often | `encrypted_user_content` |

**Group 3 — needs the model.** Reading, not counting. Belongs in the existing
Mirror run, which already reads everything — a separate call would be a second
pass over the same material.

| Signal | Note |
|---|---|
| Word choice and register | The owner's example. Needs defining: vocabulary range? hedging? absolutes? |
| Whether something is described or evaluated | "I was late" versus "I'm hopeless" |
| Whether an entry resolves or trails off | |
| Who appears as subject versus object | "I did" versus "it happened to me" |
| Which categories co-occur | Derivable from Group 2 counts, but reading is better at it |

**Deliberately not on this list:** anything that scores a person. No "resilience",
no "insight", no composite wellbeing index. The same line Trends refuses to cross
with severity bands, and the reason the summariser is forbidden from writing
"barely keeping it together" — see the top of this file.

### The storage question — a two-way door, corrected 2026-10-12

**This section first called storage a one-way door. That was wrong, and the owner
corrected it.** Their argument, which holds: if Memory as discussed turns out to be
redundant, the table can be wiped with no consequence and Memory repurposed or
hidden.

Why it holds. The one-way-door label belongs to data that cannot be regenerated —
an encryption key, a summary of an entry that has since been destroyed, an
instrument key with responses behind it. **Measurements are derived.** Counts,
lengths, frequencies and distributions can be recomputed from entries, summaries
and check-ins whenever they are wanted. Wiping them loses nothing permanent. The
hand-typed items that exist are restorable from backup and re-typeable. Changing
shape costs a migration, which is routine in this project.

**The one part that is genuinely hard to undo, and it is not storage.** Mirror's
report run reads confirmed Memory and presents it to the model as *"Confirmed in
their Mirror"* — things the person stands behind. If measurements land in the same
rows, the model begins reading someone's numbers as their own statements about
themselves, and every report built on that is wrong in a way nothing surfaces.
That is a correctness problem, avoidable by keeping the source distinguishable
(`source` already has unused values for exactly this), and it is worth deciding
deliberately rather than discovering in a report.

The remaining cost of getting the shape wrong is a migration, plus one caveat: any
*action the person took* on those rows — an edit, a deletion — is not
regenerable, unlike the measurements themselves. If measurements are never
editable, there is nothing there to lose.

### Where it goes

Three options:

1. **Reuse `user_memory`.** Numbers stored as encrypted sentences. Cheapest to
   build, worst to query, and the `kind` enum would need a value that is not a
   kind of statement. The Keep/Remove UI would sit over rows that cannot be
   meaningfully approved.
2. **A new table.** Right shape — a key, a value, a window, a computed-at. But
   Mirror's Memory tab would then show two unrelated things, and the person has to
   understand why.
3. **Not in Memory at all.** These are trends about writing, and Mirror already
   has a Trends tab that does exactly this for check-ins. The honest reading of
   the owner's ask may be that Trends grows a second family of cards and Memory
   stays what it is.

**Option 3 is worth real consideration before 1 or 2.** The word "Memory" is doing
a lot of work in the original request, and the thing described — patterns,
correlated against wellbeing — is what Trends is.

### What happens to the Memory that exists

Needs an answer either way:

- Do hand-written facts and threads stay? They are the only thing in Memory now.
- If measurements live alongside them, what does Keep/Remove mean on a number?
- The Keep button, the "waiting on you" badges and the aside callout are all
  **dead code today** — gated on a proposed state nothing can create. They light
  up only if something proposes items. Measurements would not.

### What a finding is allowed to say — build both registers, owner decides

**The owner's decision, 2026-10-12:** during this testing stage, produce **both**
the bare count and the interpreted reading, and they will judge which is
appropriate. Their reasoning on each:

- The bare count *"of the 11 highest readings with sleep logged around them, 7
  fell in a week whose median sleep was below your overall median"* — **not useful
  on its own.** Their words: *"it's just numbers - there needs to be a translation
  to a user what those numbers actually mean."* Correct, and it is why the
  "Plainly" paragraph exists and why it has never satisfied anyone.
- The causal claim *"your anxiety is worse when you sleep badly"* — **too strong.**
- What they want sits between: *"higher scores on GAD-7 questionnaires correlate
  with worse sleep patterns over time"*, or *"the topics/tone conveyed in entries
  also focuses more on the open questions/problems with less hours of sleep"*.

So three registers, and the middle one is the target:

| Register | Example |
|---|---|
| **Counted** | "7 of your 11 highest GAD-7 readings fell in weeks averaging under 6 hours of sleep." |
| **Read** (target) | "Your higher anxiety scores have tended to fall in weeks averaging under 6 hours of sleep — 7 of 11." |
| **Causal** (not allowed) | "Your anxiety is worse when you sleep badly." |

The middle register keeps the count *in* the sentence rather than instead of it.
That is the move: it translates without detaching from the evidence, so the reader
can disagree with the reading and still see the numbers behind it.

#### Quantities, never relative words — owner's instruction 2026-10-12

My draft said "weeks with **less sleep**". The owner's correction, and it is a
sharper rule than the one I had:

> *"Go with quantity, not even a relative — people have varying ranges of average
> sleep, I myself usually sit around 6 hours average. It's not that it's healthy,
> it's just my baseline — so less is relative, but a quantity is absolute."*

"Less sleep" is meaningless without knowing whose baseline, and the baseline is
not a health claim — it is just what that person's sleep is. "Under 6 hours" is
absolute and checkable. So:

- **Say the quantity.** "averaging under 6 hours", "across 11 days", "in 7 of 11".
- **Not a comparison word.** Not "less", "more", "worse", "better", "low", "poor".
- **Relative framing is a later feature, not a wording choice.** Once there is
  enough history to know a person's own average, "below your 6.2-hour average"
  becomes available *and meaningful* — because the comparison is to them rather
  than to nothing. Until then it is a comparison with no second term.

This also settles the "worse sleep" objection rather than arguing it: the word
goes, because it is relative, not because it is a judgement. Same reasoning, and
it generalises further than the judgement argument does.

**This is rule 10 in `CLAUDE.md` extended** — that rule bans words that stand in
for a length of time. This bans words that stand in for a comparison. Same shape,
same reason: a reader cannot check a word, only a number.

The owner's second example, rewritten to the rule: *"in weeks averaging under 6
hours of sleep, your entries more often circled open questions than resolved
them."*

#### What this costs, which the test should expose rather than hide

1. **It cannot be a deterministic template, and that is accepted.** `plainly()` is
   a template precisely so no model writes prose about someone's mental-health
   scores. The owner's decision, 2026-10-12: a model may write it, **but the
   guardrails go in the system prompt** so the output is consistent rather than
   improvised per run. That is how every other generated surface here already
   works — the summariser's categories are a closed list the parser enforces, the
   report's areas likewise. The same approach applies: state the rules above as
   prompt rules, and enforce in code whatever can be enforced.
2. **A floor applies to relationship claims, not to reporting readings.** Refined
   from my original blanket objection, at the owner's direction: *"it's still good
   to assess any of the framework readings with the data that was accrued in that
   time period."* Correct, and the two are different acts:
   - **Reporting what was recorded** is fine at any number, with the number
     stated. "You answered GAD-7 twice in this window, scoring 14 and 12." Trends
     already does exactly this with its gathering state.
   - **Claiming a relationship between two signals** needs enough points to be
     one. Across 2 readings it is not a correlation in any register, and a
     confident sentence about noise teaches the wrong lesson about the feature.

   As of 2026-10-12: 2 GAD-7 readings, 2 PHQ-9, 1 PWI, 9 check-ins. So reporting
   works today; relationships do not yet. (There was also 1 SWLS reading. The
   instrument was removed on 2026-10-12 as redundant beside the PWI, and its
   responses deleted at the owner's instruction.)

A relationship between writing behaviour and a wellbeing score is more tempting
and more fragile than either signal alone, because the sample is one person and
that person reads the result. That is the argument for the floor on relationship
claims — not against the feature, and not against reporting readings.
